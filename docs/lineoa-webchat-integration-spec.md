> เอกสารสำหรับทีมที่ดูแล **LINE OA ของบริษัท** (ผู้ส่งมอบตัวตนพนักงาน)

## 1. บริบทและเป้าหมาย

ตามที่ประชุมกันไว้: พนักงานจะไม่แจ้งปัญหา IT ผ่านกลุ่ม LINE อีกต่อไป แต่จะเข้าผ่าน
**ปุ่ม Helpdesk บน LINE OA ของบริษัท** ซึ่งพนักงานลงทะเบียนไว้แล้ว เมื่อกดปุ่ม
LINE OA จะเปิด **หน้าเว็บแชท** ของระบบ Helpdesk พร้อมส่ง **รหัสพนักงาน** มาให้
ระบบ Helpdesk จะนำรหัสไปดึงชื่อ/แผนก/สถานที่จาก Employee Database เอง
แล้วให้พนักงานคุยกับ AI เพื่อแก้ปัญหาเบื้องต้น / เปิด-ติดตาม-ปิด Ticket

```
[พนักงาน] → [LINE OA: ปุ่ม Helpdesk]
                    │  ส่ง "ตัวตน" มาให้ (หัวข้อ 3)
                    ▼
            [Helpdesk Web Chat]
                    │  รหัสพนักงาน → ยิง Employee DB เอง (มีอยู่แล้ว)
                    ▼
         [AI intake → เปิด/ติดตาม/ปิด Ticket → itamtv]
```

**สิ่งที่ฝั่ง Helpdesk รับผิดชอบเองทั้งหมด** (ไม่ต้องรบกวนทีม OA):
หน้าเว็บแชท, ตัว AI, การดึงข้อมูลพนักงานจาก Employee DB, การเปิด/ปิด Ticket,
การส่งเคสต่อเข้า itamtv, SLA และรายงาน

**สิ่งที่ต้องการจากทีม OA** มีเพียง 3 อย่าง คือ **(ก)** วิธีส่งมอบตัวตนที่ตรวจสอบได้
**(ข)** วิธีเปิดหน้าเว็บแชท **(ค)** ช่องทางส่งข้อความแจ้งกลับหาพนักงาน

## 3. (ก) การส่งมอบตัวตน — หัวข้อสำคัญที่สุด

หน้าเว็บแชทของเราอยู่บนอินเทอร์เน็ตสาธารณะ ใครก็เปิด URL ได้ ดังนั้น
**รหัสพนักงานที่ส่งมาแบบข้อความธรรมดาเรารับไม่ได้**

> ตัวอย่างที่รับไม่ได้: `https://helpdesk.example.com/chat?emp_code=90004`
> ใครแก้ URL ก็สวมสิทธิ์เปิดเคสในชื่อคนอื่นได้ทันที และระบบเรามีขั้นตอน
> **ขออนุมัติจากหัวหน้าตามแผนก** ความเสียหายจึงไม่ได้จบที่เคสผิดคน

ขอเลือก **1 ใน 2 แบบ** ด้านล่าง (เรียงตามที่เราแนะนำ):

### แบบ A — LIFF + ID Token (แนะนำ)

เปิดหน้าเว็บแชทเป็น **LIFF app** แล้วให้หน้าเว็บส่ง `id_token` จาก LIFF SDK มาให้เรา
เราตรวจลายเซ็นกับ LINE เอง (`https://api.line.me/oauth2/v2.1/verify`) → ได้ `userId` ที่ปลอมไม่ได้

จากนั้นขอ **API ฝั่ง OA แบบ server-to-server** เพื่อแลก `userId` เป็นรหัสพนักงาน:

```
GET  {OA_BASE_URL}/api/line-users/{userId}
Authorization: Bearer <API key ที่ออกให้ Helpdesk>

200 OK
{
  "line_user_id": "U780dfa390ec386e71f70a109d4ee745c",
  "emp_code": "90004",
  "registered_at": "2026-05-02T09:11:00+07:00",
  "active": true
}
404 → ยังไม่ได้ลงทะเบียนกับ OA
```

**ข้อดี:** ตัวตนพิสูจน์โดย LINE เอง, รหัสพนักงานไม่เคยผ่านมือ browser ปลอมไม่ได้เลย,
ฝั่งเรามีโค้ดตรวจ ID token ใช้งานจริงอยู่แล้ว (ใช้กับฟอร์ม LIFF ปัจจุบัน)

**สิ่งที่ต้องการ:** LIFF ID + Channel ID ของ LINE Login channel, base URL + API key ของ endpoint ข้างบน

### แบบ B — Signed Token บน URL

ถ้าไม่สะดวกทำ API ให้ ขอเป็น **JWT ที่ลงลายเซ็นแล้ว** แนบมากับ URL ตอนเปิดหน้าเว็บ:

```
https://helpdesk.example.com/chat#t=<JWT>
```

Payload ที่ขอ:

| claim | ตัวอย่าง | หมายเหตุ |
|---|---|---|
| `iss` | `"amarin-line-oa"` | ผู้ออก token |
| `aud` | `"it-helpdesk"` | กันเอา token ไปใช้ข้ามระบบ |
| `sub` | `"U780dfa..."` | LINE userId |
| `emp_code` | `"90004"` | รหัสพนักงาน |
| `iat` / `exp` | — | **อายุไม่เกิน 5 นาที** |
| `jti` | uuid | กันใช้ token ซ้ำ (เราจะเก็บกันเล่นซ้ำฝั่งเรา) |

- อัลกอริทึม: **RS256** (ขอ JWKS URL เพื่อดึง public key และ rotate ได้) หรือ HS256 + shared secret ถ้าจำเป็น
- ส่งมาใน **URL fragment (`#`)** ไม่ใช่ query string — fragment ไม่ติดไปกับ referer/access log
- token ใช้ครั้งเดียวเพื่อเปิด session เท่านั้น หลังจากนั้นเราออก session ของเราเอง

## 5. (ค) การแจ้งกลับหาพนักงาน — ต้องตอบก่อนออกแบบ

| เหตุการณ์ | เกิดเมื่อ |

| ผลอนุมัติคำขอเบิกอุปกรณ์/ขอสิทธิ์ | หลังหัวหน้ากดอนุมัติ |
| ติดตามอัตโนมัติ (ถามว่าแก้ได้ไหม) | 10 นาทีหลังบอทแนะนำวิธีแก้ |

| # | คำถาม | คำตอบ |
|---|---|---|
| 5.1 | Helpdesk push ข้อความ 1-1 หาพนักงานผ่าน OA ของบริษัทได้ไหม | ☐ ได้ ☐ ไม่ได้ |

## 6. เรื่องภายในที่ต้องตัดสินใจคู่กัน (ไม่ใช่คำถามถึงทีม OA)

**กลุ่ม LINE ของทีมช่าง IT** — ปัจจุบัน "ห้ามใช้กลุ่ม" ที่ตกลงกันหมายถึงกลุ่มที่พนักงาน
ใช้แจ้งปัญหา แต่ทีมช่างเองใช้กลุ่ม LINE เป็นหน้างาน: การ์ดเคสใหม่เด้งเข้ากลุ่ม
ช่างกด "รับงาน" แล้วระบบจึงสร้างเคสใน itamtv ด้วยสิทธิ์ของช่างคนนั้น และกด "ปิดเคส" ได้จากตรงนั้น

ต้องยืนยันว่านโยบายครอบคลุมกลุ่มนี้ด้วยหรือไม่ — ถ้าครอบคลุม ต้องย้ายการรับงาน
ไปที่ push 1-1 หาช่างรายคน หรือใช้ Dashboard อย่างเดียว ซึ่งเป็นงานออกแบบอีกก้อน

## 7. สิ่งที่ฝั่ง Helpdesk จะสร้าง (เพื่อให้เห็นภาพตรงกัน)

```
POST /api/chat/session     ← รับ id_token (แบบ A) หรือ JWT (แบบ B)
                             → verify → ดึงข้อมูลพนักงานจาก Employee DB
                             → ออก session token ของเรา (อายุ 8 ชม.)
POST /api/chat/message     ← ข้อความ/รูปจากผู้ใช้ → ตอบกลับจาก AI
GET  /api/chat/history     ← ประวัติบทสนทนา + สถานะเคสของคนนั้น
```

**ความปลอดภัย:** ทุก endpoint ต้องมี session token, ผูก session กับ `emp_code` ที่ผ่านการยืนยัน
เท่านั้น (ผู้ใช้ระบุ emp_code เองไม่ได้), บังคับ HTTPS, จำกัดอัตราการเรียก

**ข้อมูลที่เราเก็บ:** รหัสพนักงาน, LINE userId, บทสนทนา, ข้อมูล Ticket
**ไม่เก็บ:** ชื่อ/แผนก/เบอร์ (ดึงสดจาก Employee DB ทุกครั้ง ไม่ cache)

## 8. ข้อมูลขั้นต่ำที่ต้องได้ต่อ 1 session

| ฟิลด์ | จำเป็น | ใช้ทำอะไร |
|---|---|---|
| `emp_code` | **ใช่** | ดึงชื่อ/แผนก/ตำแหน่ง/อาคาร/ชั้น จาก Employee DB + ระบุผู้แจ้งใน itamtv |
| `line_user_id` | **ใช่** | ใช้ push แจ้งเตือนกลับ + ผูกกับข้อมูลเดิมในระบบ |
| ชื่อ-นามสกุล | ไม่ | เราดึงจาก Employee DB เอง (ส่งมาด้วยก็ดี ไว้ cross-check) |

**กรณีที่ต้องนิยามให้ชัด:**
- พนักงานยังไม่ลงทะเบียนกับ OA → OA ส่งอะไรมา / ให้เราแสดงข้อความอะไร
- ส่ง `emp_code` มาแต่ Employee DB หาไม่เจอ (คนใหม่ยังไม่เข้าระบบ / ลาออกแล้ว)
- พนักงาน 1 คนมี LINE หลายบัญชี หรือเปลี่ยนเครื่อง/บัญชีใหม่
